# Architecture

## Module layout

```
src/
  shared/        small shared types and utilities (no dependencies)
  engine/        match simulation: seeded RNG, action-level engine, events, stats (pure)
  game/          career domain: clubs, players, leagues, fixtures, seasons, transfers (pure)
  commentary/    match commentary templates per locale and grammar helpers
  i18n/          locales (en, sv), typed keys, formatting
  platform/      adapters: SaveStore (memory, IndexedDB, later Tauri), file export/import
  ui/            React app shell, screens, components
  ui/match-view/ three.js momentum terrain, momentum chart, feed, stats panel
  main.tsx       composition root: wires platform adapters into the app
e2e/             Playwright tests
```

Allowed dependencies (enforced by dependency-cruiser):

```
engine     -> shared
game       -> engine, shared
commentary -> engine, i18n, shared
platform   -> shared, game (types only)
ui         -> game, engine (public index only), commentary, i18n, platform, shared
```

## Match engine

One engine simulates every match: the deterministic, seeded, action-level engine in `src/engine/action/` (design below). Players, not team ratings, drive the simulation. It replaced the original zone engine (v1, a state machine over team phase ratings) in M5b; v1 and its zone-based tests, fixtures and balance suite were deleted by #167. Only its output survived in a different role: the momentum terrain still draws zone-style events, produced from action events by an adapter (see Consumers).

- `createActionMatch(input, seed, options?)` returns an `ActionMatch` with `advanceTo(time)`, `applyChange(change)` (substitutions, tactics), `resume()` (second half), the accumulated `events`, `state` and `changes`.
- A match is fully reproducible from `seed + input + list of timed changes`. Saves store results, not logs.
- `TeamTactics` (`src/engine/tactics.ts`) has four settings, each with a neutral middle level (`NEUTRAL_TACTICS`: balanced, medium, normal, normal): mentality (defensive, balanced, attacking), pressing (low, medium, high), width (narrow, normal, wide) and tempo (slow, normal, fast). How the engine uses them is described under "Tactics and home advantage".
- Periods: first half, half-time (the simulation pauses until the user resumes), second half, added time. Kickoff after goals and at the start of each half.
- `MatchInput` has `engineVersion: 2`. The field is kept for a future engine and is also stamped on every recorded `Result` (`1` on results from before #167 stays a label; finished matches are never replayed).

## Engine design

### Constraints

- The engine only imports `src/shared`. It cannot import `Player`, `Formation` or `Lineup` from `game`, so it defines its own input types and `game` maps into them.
- The engine knows players, not clubs: fitness and form already produce effective attributes (`player-condition.ts`) and those are the player attributes the engine gets.
- Saves hold only the `Career` (results as goals, no event logs), so the event log needs no format in saves.
- The CI gates: `engine` is pure, no `Math.random` or clocks, `ui` uses `engine` only through `index.ts`, and balance tests are not weakened.

### Public API

- The engine code lives in `src/engine/action/` (one concept per file, own tests, own balance tests `action.balance.test.ts`). Shared small types (`Side`, `Period`, `TeamTactics`, `Rng`, pitch helpers) sit next to it in `src/engine/`.
- `MatchInput` = `{ engineVersion: 2, home, away }`: per side a `TeamSheet` = `{ name, formation, starters, bench, tactics }`. `formation` is `{ defenders, midfielders, forwards }` counts (1 GK implied; the engine does not know formation names). `starters` are 11 `EnginePlayer`s in slot order (GK first, then the lines, each line in lane order left to right). `EnginePlayer` = `{ id, position: "GK" | "DEF" | "MID" | "FWD", attributes }` with the twelve attributes (1 to 20, same names as `game`, already effective). Ids are opaque strings; names stay in `game` and `commentary`.
- `applyChange` takes `{ side, lineup?, tactics? }` where `lineup` is a new `TeamSheet` starters list (substitutions) and/or new tactics, applied from the next action, consuming no randomness, ignored after full time. It returns a result type: `{ ok: true }` or `{ ok: false, errors }` for an invalid lineup (not 11 players, not one goalkeeper, other formation lines, attribute out of range, reused ids; `validateLineup`), which leaves the match unchanged; it throws `RangeError` only for a side that is not `home` or `away`. Substituted-in players leave the bench (`apply-change-to-input.ts`); applied changes are listed in `ActionMatch.changes`, and the same `seed + input + changes` at the same moments gives the same log however time is split.
- Random streams: simulation uses `createRng(seed).fork("action-sim")`. Presentation (small position jitter in snapshots, commentary variants) uses separate forks (`"action-presentation"`, `"commentary"`) that never feed back into decisions. Added time keeps its own fork (`"addedTime"`). Forking does not consume the parent, so adding a stream never changes another.

### Event model

Pitch coordinates are metres: `x` 0 to 105 from the home goal line to the away goal line, `y` 0 to 68 across the width. Home always attacks towards +x (sides are not swapped at half-time).

Every `ActionEvent` has `time` (seconds, one decimal), `period`, `team` (the side performing the action), `type`, `actor` (player id), `target` (player id, where relevant), `opponent` (the player who challenged, or the keeper), `from`, `to` (metres), `outcome`, `pressure` (0..1) and `snapshot`.

| Type | Outcomes | Notes |
|---|---|---|
| `pass` (variant `short`, `long`, `through`, `cross`) | `complete`, `intercepted`, `outOfPlay`, `incomplete` | target is the intended receiver; `keyPass` flag when it leads to a shot |
| `carry` (dribble) | `kept`, `tackled`, `outOfPlay` | |
| `shot` | `goal`, `saved`, `blocked`, `missed`, `woodwork` | carries `xg` |
| `tackle` | `won`, `lost`, `foul` | `team` is the tackler |
| `interception` | `won` | |
| `clearance` | `kept`, `outOfPlay` | |
| `foul` | `free kick`, `penalty` | `team` is the fouled side, `opponent` the offender |
| `setPiece` (variant `kickoff`, `throwIn`, `goalKick`, `corner`, `freeKick`, `penalty`) | `taken` | restart position and set-up shape, followed by the first action |
| `periodChange` | | start of half-time, second half and full time |

- `snapshot` is `{ ball: Point, players: readonly Point[] }` with 22 points (home slots 0 to 10, then away 11 to 21) taken at the moment of the action. Every player is inside the pitch. Views interpolate between consecutive snapshots; they never invent positions.
- The ball is always on the pitch or the event is an out-of-play outcome followed by the matching restart `setPiece`.
- Shot outcomes `goal` is followed by a kickoff `setPiece`. A foul in the box gives a penalty.
- Aim: about 1,900 actions per match at a mean of 3 s. Rough budget: ~1,000 passes, ~250 carries, ~25 shots, ~150 tackles, ~100 interceptions, ~50 clearances, ~24 fouls and ~100 restarts.

### Team shape

`teamShape(sheet, tactics, phase, ball, side)` is a pure function that returns the 11 positions of a side.

1. Anchor per slot from the formation (GK, lines, lanes). Defenders and midfielders spread evenly over the width; forwards stand `FORWARD_LANE_SPACING` (12 m) apart around the middle line whatever their number, so a pair or a trio is as close to goal as a lone striker (an even split of the width left 4-4-2 without a central striker and let every three-forward shape beat it, see #214).
2. Phase of play shifts the whole block: `buildUp`, `progression`, `attack`, `defending`, `transition`, `setPiece`. The phase follows possession, ball position and the last action (a turnover starts `transition` for a few actions).
3. Tactics set the parameters: **line height** (pressing and mentality), **width** (width setting) and **compactness** (pressing and mentality). Line height moves the defensive line up or down, width scales the lateral spread, compactness scales the distance between lines.
4. Ball position pulls the block: the block shifts towards the ball (vertical and lateral) and the nearest players press or support.
5. Set pieces have fixed set-ups owned by the engine: corner (takers, near-post and far-post runners, edge-of-box players, counter-attack cover), free kick (wall at 9.15 m, runners), penalty (taker, keeper on the line, everyone else outside the box and the arc), goal kick (keeper, split defenders, pressing line), throw-in (thrower, two options, markers), kickoff (own half, taker and one support in the centre circle).
6. All positions are clamped to the pitch and a minimum distance between players of the same side keeps the shape from collapsing.

Implemented in `src/engine/action/`: `team-shape.ts` (`teamShape`, `formationAnchors`, `shapeParameters`), `team-phase.ts` (`phaseOf`), `pressure.ts` (`pressureOn`) and `shape-constants.ts`, which holds every tuning value (line depths, phase shifts, tactic mappings, ball pull, minimum distance, pressure radius). The home side attacks towards x = 105; the away side is the x-mirror. Set-piece set-ups (item 5) are in `set-piece-shape.ts` (see Set pieces).

Decisions use the shape (pressure = weighted count of opponents within a few metres of the actor and of the target). The shape is a pure function of its inputs; only the snapshot jitter (at most 0.5 m, from the presentation stream, clamped to the pitch) is random, and it is added to the snapshot only, never used in a decision. Snapshots are also capped at `MAX_SNAPSHOT_SPEED` (10 m/s) from the previous one (`limit-snapshot-speed.ts`). When that leaves the actor of a pass, carry or shot more than `ACTOR_BALL_REACH` (1.5 m) from the ball, `keepActorOnBall` shows the ball `ACTOR_BALL_HOLD` (1 m) from the actor instead of moving the player, so the cap holds and the carrier stays on the ball; the decisions and event `from`/`to` are untouched.

### Decisions and outcomes

- The ball carrier builds a list of options: pass to each teammate (short, long, through, cross as variants), carry, shot and clearance. Each option gets a weight from the actor's attributes (passing, vision, dribbling, finishing, ...), the option's geometry (distance, progress, angle, space at the target), the tactics (tempo, directness, width, risk) and the pressure on the actor. The engine draws one option from the weights with the simulation stream.
- The outcome depends on actor against opponent attributes and pressure: pass accuracy from passing and ball control against interceptors' positioning and work rate along the lane; carries from dribbling and pace against the nearest defender's tackling; tackles and fouls from tackling, strength and pressure; shots from finishing, shot geometry (the existing `shotXg` idea, recalibrated), pressure and the keeper's handling and reflexes.
- Implemented in `src/engine/action/`: `build-options.ts` (`buildOptions(actor, shapes, tactics)`: a pass to every teammate with its variant, a carry and a clearance; a shot option at the goal centre with its xG), `choose-option.ts` (one `rng.next()` per choice), `resolve-pass.ts`, `resolve-carry.ts`, `resolve-challenge.ts` (tackle or foul; a foul in the attacked box gives a penalty), `resolve-interception.ts`, `resolve-clearance.ts`, `action-duration.ts` (2 to 4 s, tempo skews the draw) and `out-of-play.ts` (where the ball leaves the pitch and which restart follows), `shot-xg.ts`, `resolve-shot.ts` and `mark-key-passes.ts` (see Shots below). A resolver returns `{ outcome, ball, possession, restart? }`; `possession.slot` is absent when a dead-ball taker is chosen later. All tuning values are in `decision-constants.ts` (first guesses; the balance issue calibrates them).
- Every decision and outcome function is pure and takes the `Rng` as the last argument, so it can be tested with a scripted RNG as `transition.test.ts` does today.
- The home side gets a small, named `HOME_ADVANTAGE` constant (applied to action success, tuned in the balance issue).

### Tactics and home advantage

`tactics-parameters.ts` (`actionTactics(tactics)`) is the only place that reads the four settings; it returns named parameters: `directness`, `risk`, `shotWeight`, `wideBonus`, `centralShot`, `tempoExponent`, `passSuccess`, `lineHeight`, `compactness`, `width`, `pressRadius` (press trigger distance), `turnoverBonus` and `spaceBehind`. Neutral tactics give 0 (additive) or 1 (multipliers), pinned by a test. The tables behind the values are in `decision-constants.ts` and `shape-constants.ts`. Pressing acts on the opponent: `pressRadius` is the distance within which the pressing side's players count for pressure (`pressureOn(..., radius)`), `turnoverBonus` raises interceptions and lost carries against a build-up in the opponent's own half, and `spaceBehind` raises through passes and carries of a side that has just won the ball (`ActorContext.transition`, `foeTactics`). Tempo shifts pass completion (`passSuccess`) and the action duration draw; width scales the weight of shots from the central channel; mentality scales shot and risky-pass weights and compactness. Tactics are read from the sheet of each side at every action, so `applyChange` tactics take effect from the next one.

`HOME_ADVANTAGE` (`decision-constants.ts`, 0.009 after calibration) is added to the success chance of the home side's passes, carries, interceptions and tackles through `homeEdge(side, advantage?)`; an advantage of 0 gives exactly the match without it. It is not applied to shots yet.

### Shots

- `shotXg(from, pressure, bodyPart?)` (`shot-xg.ts`, exported as `actionShotXg`) is a logistic model of the distance to the goal centre and the angle the posts subtend, in the attacking frame (`toAttackingFrame` mirrors the away side so both attack towards x = 105). Pressure removes up to half the value, headers keep 0.6, and the result is capped at `MAX_SHOT_XG` (0.6).
- The shot option weight is `SHOT_WEIGHT_GAIN x xG x finishing x mentality`, and 0 below `SHOT_MIN_XG`, so players far from goal never choose it.
- `resolveShot(input, rng)` (input holds the shooter, keeper, outfield defenders, xG and pressure): one draw picks the class. Below `goalChance` (xG x finishing factor x keeper factor) it is a goal; the rest is split between woodwork, blocked (needs a defender within `SHOT_BLOCK_RADIUS` of the lane), saved and missed. A save or a block draws once more: corner, catch or rebound for a save; corner or a loose ball for the blocker for a block. A miss gives a goal kick without a draw, woodwork a rebound. A rebound goes to the nearest of the shooter and the defenders.
- A penalty uses `PENALTY_XG` (0.76) and `penalty: true` (no blockers); the keeper still decides.
- `markKeyPasses(events)` sets `keyPass` on a completed pass whose very next action is a shot by its receiver on the same team.

### Match loop

Implemented in `create-action-match.ts` (periods, clock, added time) and `play-action.ts` (one action). Every action is one event at a fixed time; the next action follows `actionDuration` (2 to 4 s) later, so the log does not depend on how `advanceTo` is split. The match starts with a kickoff event at 0 s; a period ends with a `periodChange` event, and `resume` emits `periodChange` plus a kickoff for the side that did not start. Added time uses `fork("addedTime")`. A goal is followed by a kickoff for the conceding side; out-of-play outcomes by the matching restart `setPiece` (taker and set-up from `set-piece-shape.ts`, see Set pieces). Each action first draws a challenge chance from pressure (`CHALLENGE_PRESSURE_GAIN`): a tackle, or a `foul` event for a foul. A pass interception is the `pass` event with outcome `intercepted` and `opponent` set; a lost carry is the `carry` event with outcome `tackled`. The ball carrier is placed on the ball in the shapes. Snapshot jitter comes from `fork("action-presentation")` (`snapshot.ts`).

### Set pieces

`set-piece-shape.ts` (`setPieceShape(kind, side, spot, sheets)`, tuning values in `set-piece-constants.ts`) returns `{ home, away, taker, targets, wall }`: the 22 positions of a dead ball, the taker's slot and the slots the first action needs. Shapes are built in the taker's attacking frame from each side's plain `setPiece` shape and mirrored for the away side; roles (taker, runners, wall, markers, pressing line) go to the nearest free players (lowest slot on ties), everyone else keeps the plain position within the limits of the kind. Unassigned players that would stand closer than `MIN_PLAYER_DISTANCE` to anyone are moved apart by `separate` (`separate-players.ts`, deterministic, within the limits of the kind); role points never move, so two role players can still be closer (the wall, a post defender next to a marker), and the taker may stand next to anyone. `roles` lists the slots on fixed role points. Kickoff: own half, taker and one support in the centre circle, opponents outside it. Throw-in: thrower on the line, two options and a marker goalside of each. Goal kick: keeper, two split defenders, a four-player pressing line outside the box. Corner: near and far post and penalty-spot runners, two at the box edge, two counter cover; keeper, two post players and markers defend. Free kick: a four-player wall at 9.15 m on the line to goal when within `FREE_KICK_RANGE` (32 m) of the goal, runners; no wall out of range. Penalty: taker on the spot, keeper on the line, everyone else at x <= 84.5 (outside box and arc). Takers (`restartTaker`): keeper for goal kicks, nearest outfield player for throw-ins, best finisher for penalties, passing plus vision for corners and free kicks, passing for the kickoff.

The `setPiece` event's snapshot is the set-up. The set-up stays in `PlayState.setUp` for the next action, which is the kind's first action and draws no challenge: a cross from a corner, a short throw, a long goal kick (the receiver is drawn from `targets` with the simulation stream), a direct shot for a free kick in range (xG with `FREE_KICK_SHOT_PRESSURE`, the wall can block), the penalty shot. A free kick out of range and the kickoff go on as open play from the set-up positions. A foul inside the attacked box is a penalty, elsewhere a free kick (`resolveChallenge`); `ActionMatchState.fouls` counts fouls committed per side.

### Performance and the fast path

- A full match (about 1,900 actions) must simulate in under 50 ms on a laptop (median of repeated runs after warm-up), so other matches of a round can be simulated in the background.
- `createActionMatch(input, seed, { detail: "fast" })` (`"full"` is the default) skips building snapshots, the snapshot jitter and its `"action-presentation"` stream; `ActionEvent.snapshot` is then absent. It keeps every event, so stats, ratings and commentary work on a fast log. It must give the same score, the same event types, times, actors, outcomes and xG as `detail: "full"`; a test compares both over 200 seeds and several inputs. Positions that decisions need are computed on demand by the same pure shape function, so the fast path cannot diverge. `game` uses the fast path for matches that are not viewed; balance tests use it too.
- Measured with `npm run bench:engine` (bundles `performance.bench.ts` and runs it in plain Node; Vitest's module wrapper roughly doubles the time): median of a whole match 29 ms fast and 31 ms full, p95 about 42 and 47 ms. `performance.perf.test.ts` fails only above 150 ms to leave room for slow CI runners; it runs alone and serially via `npm run test:perf` (`vitest.perf.config.ts`, a separate CI step) and is excluded from `npm test`, so parallel test files cannot slow it down. The season budget (26 matchdays of 13 background matches, `26 * 13 * 50 * 3` ms) runs there too, in `src/game/complete-matchday.perf.test.ts`; `complete-matchday.test.ts` keeps only its behavioural assertions, so neither `npm test` nor Stryker's instrumented dry run asserts wall-clock time. The cost is the shape code, called every action: `keepApart` skips the `Math.hypot` when one axis already exceeds the minimum distance and stops once a pass pushes nobody, `pressureOn` rejects opponents on one axis first, and the formation anchors are cached per formation object. These change no results (a hash of 40 full logs was identical before and after).

### Consumers

- **Stats:** `computeActionStats(events, upTo)` (`action-stats.ts`) returns `{ teams, players }`. `teams` has possession and field tilt (time the ball stayed where, and with whom, the last event left it; a lost pass, carry or tackle hands it over; half-time and full time stop the clock; tilt from the ball's `to` x against the halfway line), shots, on target (goal or saved), xG, corners, fouls committed, throw-ins, goal kicks, passes, completed passes and pass completion per side. `players` is keyed by id with passes, completed passes, completion, key passes, shots, on target, xG, goals, tackles won, interceptions, clearances and fouls committed. It counts only events up to `upTo`, so the stats at t equal those of the log truncated at t (a key pass whose shot lies after the cut-off is not counted; `leadsToShot` is shared with `markKeyPasses`). `playerRatings(events, players)` (`player-ratings.ts`) gives a 1 to 10 rating per listed player id from a 6.0 baseline; weights are named constants in `rating-constants.ts` (goal +1, key pass +0.3, progressive completed pass (10 m or more towards the attacked goal) +0.1, tackle won +0.2, interception +0.2, save +0.3; lost carry or tackle -0.15, missed shot of 0.3 xG or more -0.3, foul -0.2, goal conceded -0.5 for the keeper named on the shot). Both are pure functions over the log.
- **Momentum terrain:** an adapter `toZoneEvents(actionEvents)` in `src/engine/action/` maps action events to `ZoneEvent`s (`src/engine/zone-event.ts`, the terrain's input: kickoff, progress, lateral, turnover, shot, goal, corner, foul, periodChange) (a forward pass or carry becomes `progress`, a sideways one `lateral`, a change of possession `turnover`, shots, goals, corners, fouls and period changes map one to one, intensity from danger and xG). The terrain and `momentumSeries` read these zone events. The terrain is never fed raw action events. Details (`to-zone-events.ts`): `team` is the side that has the ball afterwards (`holderAfter`), the position is where the ball ends up (shots: where they were taken), a goal is a `shot` plus a `goal` and woodwork a miss; any other action or restart (throw-in, goal kick, free kick, penalty) is a `turnover` when the ball changes hands, else `progress` when it moved at least `FORWARD_MINIMUM_METRES` (3 m) towards the attacked goal, else `lateral`; intensities come from danger and xG. `MatchScreen` renders `MatchLayout` from the adapted events; `useMatchPlayback` appends each tick's new events to one list (`eventCount` signals growth) instead of copying the log.
- **Match screen stats and ratings:** `ActionStatsPanel` shows `computeActionStats(events, matchTime)` (possession, shots, on target, xG, corners, fouls, passes, pass completion, key passes); at full time `PlayerRatings` (`data-testid="player-ratings"`) lists everyone who played (starters plus players brought on by applied changes) with `playerRatings`, goals, key passes, shots and xG, the user's side first, each side sorted by rating (`buildRatingRows`), the best-rated player marked as player of the match. Ratings are derived, never saved. The half-time panel shows the same `ActionStatsPanel` for the first half; there is one stats source, `computeActionStats`.
- **Commentary:** `generateActionCommentary(events, context, seed)` in `src/commentary` names players for chances, key passes, tackles, saves, goals and set pieces in `en` and `sv`, with its own `"commentary"` stream. `context.players` maps id to display name. A goal's scorer comes from the event.
- **Classic 2D view:** a flat pitch with 22 players and the ball, drawn from interpolated snapshots, with passing chains (recent completed passes of a team as lines) and set-piece line-ups (the engine's set-up positions are shown while the restart is taken). It is an alternative to the momentum terrain, chosen with a toggle on the match screen. `interpolateSnapshot(events, time)` (`src/ui/match-view/interpolate-snapshot.ts`) interpolates linearly between the surrounding snapshots, holds the nearest one outside the log and snaps at set pieces, period changes and kickoffs; `ClassicPitch` draws it through an injectable `PitchRenderer` (canvas 2D by default). The view toggle (`data-testid="view-toggle"`, choice in `sessionStorage`) switches between the two views.
- **Scorers:** `goalScorersOf(events)` (`src/game/goal-scorers.ts`) lists the shooter of every goal in order. `simulateFixture` stores it in `Result.scorers` and `MatchScreen` hands it over in `FinishedMatch.scorers`; `summariseSeason` tallies recorded scorers by player name and club and draws scorers with `pickGoalScorers` only for results without them (saves before schema v6).
- **Game:** `matchInputFor` builds a `MatchInput` from the squad plan and `condition`; `planHalfTime` produces an `ActionMatchChange`; `simulateFixture` and `completeMatchday` stamp `engineVersion` and use the fast path. The season's top scorers are not in the log (results store goals only): `pickGoalScorers` draws a scorer per stored goal, weighted by position and finishing, from its own RNG stream.

### Testing

- Unit tests with a scripted RNG per decision and outcome function; exact expectations on deterministic parts (shape, set-up positions, geometry).
- Property tests (dev dependency `fast-check`, MIT; run counts are small by default and raised in the nightly run): for random valid inputs and seeds, **the ball is always on the pitch or the event is an out-of-play outcome**, **there are exactly 22 players in every snapshot**, **every position is within the pitch**, **time never decreases and gaps between actions are 2 to 4 s (except period changes)**, **the same input and seed give the same log however time is split**, **fast and full detail agree**, **score equals the number of goal events**, and **possession alternates only through a turnover event**.
- CI split: `npm run test:balance` runs everything; `npm run test:balance:fast` skips the 81-combination files `action-no-dominant-tactic-*.balance.test.ts`. The PR runs the fast script as one job, or, for PRs that touch `src/engine/**`, `vitest.balance.config.ts` or a `*.balance.test.ts`, or carry the `full-balance` label, the full suite as a matrix of parallel jobs (#219). `scripts/balance-groups.mjs` lists the groups (`game`: the formation, league and season suites; `tactics-attacking`, `tactics-balanced`, `tactics-defensive`: three combination files each plus one of the engine suites) because `vitest --shard` splits by file count, not duration; `npm run test:balance:group -- <name>` plays one group, and `balance-groups.test.ts` fails if a balance file is in no group or the workflow matrices differ from the groups. A final job named `Balance` needs the scope, fast and shard jobs and fails if any ended in anything but success or skipped, so the required check and auto-merge are unchanged. `nightly.yml` runs the same matrix (`balance-shard`, each uploading its log and outcome); job `Balance (full)` (`balance-full`) joins them with `balance-groups.mjs merge` into one `balance.log` and fails if a shard failed or left nothing, so the status entry, badge (goals, shots and home win rate from the average-vs-average table) and the issue from `scripts/nightly-balance-issue.sh`, which names the failed shards, stay one `balance` result.
- Balance tests (`action.balance.test.ts`, at least 1,000 seeded matches, average vs average unless noted): goals 2.4 to 3.0, shots 20 to 30, total passes 800 to 1100, pass completion 75% to 88%, corners 8 to 12, fouls 20 to 28, throw-ins 35 to 50, penalties 0.2 to 0.4, total xG within 15% of goals, home win rate 42% to 48%; a clearly stronger team wins at least 55% (and the weaker team at least 10%); each tactic setting moves its target statistic (high press gives more high turnovers and more shots conceded on counters than low press, wide gives more crosses and corners, fast tempo more actions in less time, and so on) and no tactic combination dominates.
- Balance harness: `simulateActionBalance(input, matches, baseSeed)` (`action-balance.ts`) plays seeded matches on the fast path and returns per-match and per-side averages (goals, shots, shots on target, xG, passes, completed passes, pass completion, corners, fouls committed, throw-ins, goal kicks, penalties awarded, high turnovers, shots conceded within 20 s of a turnover, crosses, central shots, actions) and home/draw/away rates; `formatBalanceTable` prints a PR-ready markdown table. The per-match counts are pure functions over the log in `action-balance-metrics.ts` (`matchMetrics`). A turnover is a pass intercepted, a lost carry, a won tackle or an interception; it is "high" when the ball is won in the opponent's half.
- Calibration: all tuning values live in `decision-constants.ts` and `shape-constants.ts`. Besides the first guesses it added a few named levers: `LONG_PASS_FACTOR` (the long ball is the exception), `PENALTY_AREA_FOUL_FACTOR` (defenders stay on their feet in their own box), `CROSS_DEFLECTED_CORNER_SHARE` and `CROSS_INTERCEPTED_CORNER_SHARE` (crosses that end behind the goal line give corners) and `MENTALITY_SPACE_BEHIND` / `WIDTH_SPACE_BEHIND`, which join `PRESSING_SPACE_BEHIND` in the counter weights (through passes, carries and shots of a side that has just won the ball), so every setting that gains something also leaves something open.
- Calibration for formations and mixed-strength leagues (#214, #215): the game-level balance tests (`formation.balance.test.ts`, `league.balance.test.ts`, `season.balance.test.ts`) play generated leagues, where the first calibration (average against average) did not hold. Findings and levers: (1) formations with an odd number of forwards had a striker on the middle line and won 58% to 75% against 4-4-2, whose pair stood at y = 23 and 45; `FORWARD_LANE_SPACING` fixed it (all six formations now within 29% to 45% wins and losses against 4-4-2). (2) Central forwards raised the shot quality, so `XG_INTERCEPT` went from -2.1 to -3.1 and `SHOT_WEIGHT_GAIN` from 12 to 20 (goals and shots back in range); the shot model gives about 0.03 xG from 11 m on the middle line. (3) A gap between clubs inflated goals and wins: `PASS_SKILL_GAIN` 0.3 to 0.15, `PASS_RECEIVER_GAIN` 0.1 to 0.05 and `CARRY_SKILL_GAIN` 0.25 to 0.12 let attribute gaps compound less over the many passes and carries of a possession, and `SHOT_FINISHING_GAIN` 0.5 to 0.25 and `FINISHING_GOAL_GAIN` / `KEEPER_GOAL_GAIN` 0.6 to 0.4 stop finishing and goalkeeping from multiplying a gap twice (14 against 10 now wins about 70% with 2.8 goals in total, 18 against 10 wins 86% with 3.5). The tackle and interception gains are unchanged, and none of these gains affects an average-against-average match. (4) Open-play crosses were almost absent (0.16 per team and match, nearly all crosses came from corners), so wide play could not make more crosses: `CROSS_MIN_DEPTH` 70 to 60 makes wide midfielders cross targets (15 per team and match, 36 with wide play and `WIDTH_WIDE_BONUS.wide` 2.5, 4 with narrow), `WIDTH_SCALE.wide` is 1.35 (it stretches every line except the forwards, who stay central whatever the width) and `CROSS_DEFLECTED_CORNER_SHARE` / `CROSS_INTERCEPTED_CORNER_SHARE` went to 0.2 / 0.6, which keeps about 11 corners per match and gives wide play more corners than neutral. `PASS_OUT_SHARE.short` 0.25 to 0.3 and `PENALTY_AREA_FOUL_FACTOR` 0.4 to 0.3 restore throw-ins (about 37) and penalties (0.34) after the box saw more play.
- Nightly status: every `nightly.yml` job writes `result-<job>.json` (`scripts/nightly-status.mjs result`: job, outcome, date, commit, run URL; goals, shots and home win rate per match for balance, the score for mutation) and uploads it as an artifact. The last job `Publish nightly status` runs even if a job failed, turns the artifacts into `status.json` plus a shields.io endpoint file `badge-<job>.json` per job (`scripts/nightly-status.mjs publish`) and commits them to the orphan branch `nightly-status` (`scripts/publish-nightly-status.sh`, `contents: write`, never `main`). The README badges read the raw files on that branch. Mutation badge: green at 80% or more, yellow at 60% or more, red below; a failed job is red and its message names the job; a job without a result is grey. The logic is pure and tested in `scripts/nightly-status.test.ts`.
- Mutation testing: `src/engine/**` is already in `stryker.config.json`, so every file of the engine is mutated (except tests, the public index and test support such as `arbitraries.ts`, `balance-test-support.ts` and the `*-builders.ts` helpers). The shape, geometry, decision-weight and outcome functions are written as small pure functions with exact-value tests so mutants do not survive on arithmetic; a baseline for the action engine (90.6%, a lower bound) is recorded in `docs/mutation-baseline.md` and survivors are treated as missing tests. `npm run test:mutation:action` mutates only `src/engine/action` (about two hours); both configs fail below 80%.
- Nightly mutation shards (#209): the nightly job runs the engine-wide mutation test as parallel shards, so the whole run is done in two hours at most (the aim is one). `nightly.yml` has a job `mutation-plan` (it runs `node scripts/mutation-shards.mjs --plan`, whose outputs are the job matrix and the shard count), a matrix job `mutation-shard` (`stryker.shard.config.json`, 120 minute limit, no break threshold per shard, JSON report as artifact `mutation-shard-<n>`) and a merge job `mutation` ("Mutation testing (engine)") that keeps the job key the status job waits for. The plan balances **estimated minutes**, not file size: the first sharded run (8 shards of equal size) took from 3 to over 200 minutes per shard, because a mutant re-runs every test that covers it and files such as `create-action-match.ts` and `team-shape.ts` are covered by the slow whole-match tests. The estimates are in `scripts/mutation-weights.json` (a file that is not listed gets its size times a default, and a test fails until it is listed). A file above 25 estimated minutes is cut into Stryker line ranges (`file.ts:10-80`) that start at top-level declarations, so no mutant is lost; a file that cannot be cut that way (one big function) stays one unit. Units go heaviest first into the lightest shard, and the shard count follows the work (about 30 minutes per shard including 5 minutes of setup, at most 16, so the nightly stays within 20 simultaneous jobs). `scripts/merge-mutation-reports.mjs` adds the shard reports into one score (Stryker's formula: killed and timeout over killed, timeout, survived and no coverage), applies `thresholds.break` of `stryker.config.json` to the merged score, prints the measured minutes of every shard with its files (to refresh the estimates) and the wall time of the longest shard, and fails and names a shard that left no report (failed, timed out or cancelled) or a plan that gave no shard count. `nightly-status.mjs` reads the score and the wall time (`metrics.mutationScore`, `metrics.durationMinutes` in `status.json`). `nightly-workflow.test.ts` keeps the plan, shard and merge jobs consistent. `npm run test:mutation` still runs the whole engine as one job locally.

### History

The engine was built as milestone M5b ("action-level match engine", epic #145) next to the zone engine and became the only engine in #167. Careers saved before that moved to it through the schema v5 migration (see Persistence). The zone engine's `neutral-event-logs.json` fixture and regression test, its balance suite, `FORMATION_OFFSETS` and the seven derived phase ratings were deleted with it.

## Team ratings from a lineup

The engine plays individual players, so the ratings shown in the club, squad and new-career screens are descriptive, not inputs to a simulation. `src/game/line-ratings.ts` derives them from the same attributes the engine uses:

- A player's overall (`overallIn`, `player-overall.ts`) is the mean of the key attributes of their position (GK: handling, reflexes; DEF: tackling, positioning, strength; MID: passing, vision, ball control, work rate; FWD: finishing, pace, dribbling), 1 to 20.
- `lineRatings(starters)` rescales the mean overall of each line (goalkeeping, defence, midfield, attack) and of all eleven (overall) from 1..20 to 0..100. A line without players rates 0. The formation matters because it decides how many players, and which, stand in each line.
- `deriveLineRatings(players, lineup, condition)` uses the starters' effective attributes (fitness and form from `condition`; a missing entry is neutral) and throws `RangeError` for an invalid lineup (callers validate user input with `validateLineup`). `deriveClubLineRatings(club, players)` rates a club's best eleven (4-4-2) at full condition; `clubRating` in the new-career screen is its `overall`, rounded.
- Formations are real shapes in the engine (`formationShape`, anchor positions per slot). There are no per-formation rating offsets.
- `formation.balance.test.ts` plays every club of generated leagues with each formation against its own 4-4-2 (equal players, home and away alternating) on the action engine and expects no formation to win or lose more than 55% of its matches.

## Match view

- Consumes the event log only. It never calls engine internals.
- Height field on a grid over the pitch: each event adds a Gaussian bump that decays over time. The ball holder leaves a continuous pulse.
- Colour per vertex: blend of both teams' pressure plus a moving front (territory) between the halves.
- Goals: tall spike, shockwave ring in the scorer's colour, short pause, then reset to kickoff.
- Half-time: the pitch resets; the user makes up to five same-position substitutions and changes tactics in the half-time panel, then starts the second half.
- The match screen (`src/ui/match-view/match-screen.tsx`) composes the terrain with a scoreboard, momentum chart (`momentumSeries`), stats panel (`computeActionStats`), commentary feed and speed controls. `useMatchPlayback` advances the engine from the wall clock and stops at half-time and full time; `resume(change?)` applies the user's `MatchChange` with `applyChange` before `match.resume()`.
- Half-time panel (`half-time-panel.tsx`): given a `HalfTimeEditor` (squad, plan, condition, a `plan` function wrapping `planHalfTime`) it lists the eleven and bench with fitness and form, pending substitutions (`sub-add`, `sub-off-<n>`, `sub-on-<n>`, `sub-remove-<n>`, at most five) and the shared `TacticsEditor`. "Start second half" validates through `planHalfTime`; an error is shown (`half-time-error`) and the half does not start. With no changes it resumes without a plan, exactly as before. `MatchScreen` keeps the plan's `report` and passes it to `onContinue(score, report?)`; `MatchFlowScreen` forwards it to `completeMatch` and so `completeMatchday`. Nothing is persisted before the result is recorded, and leaving the match restarts it from kickoff with the saved plan; half-time tactics are not written to the career's `squadPlan`. The user's side's scorers (`matchSetup.squads`) come from the plan's starters and bench; time-aware attribution is a later improvement.
- `reference/match-view-prototype.html` is the visual reference (prototype quality, not production code). Its tuning values are a starting point.

## App shell

- Hash routing (`src/ui/routes.ts`, `use-route.ts`): `#/`, `#/league`, `#/club/:clubId`, `#/match`, `#/results`, `#/season-end`, `#/saves`, `#/squad`; unknown hashes show a not-found view. No server support needed.
- The club screen (`club-screen.tsx`, `squad-rows.ts`) is read-only: form chips, next three fixtures, season history, the line ratings (goalkeeping, defence, midfield, attack and overall, 0-100, `rating-<line>`) and the squad grouped by position and sortable per group. The best-eleven marking comes from `pickBestEleven`; attribute bands are low 1-7, mid 8-13, high 14-20, always with the number shown. An unknown club id shows the not-found view.
- The club screen also shows fitness and form columns (from `Career.condition`; both sortable).
- The squad screen (`#/squad`, `squad-screen.tsx`, `plan-rows.ts`) edits the user's `squadPlan`: a formation select (switching auto-picks), `auto-pick`, one `<select>` per starter slot (grouped by line, only players of that position) and per bench slot (players used elsewhere are disabled; the only bench keeper cannot be swapped for an outfield player), four tactic selects, the line ratings from `deriveLineRatings` (`plan-rating-<line>`) and a sortable table of all 22 players with fitness (warning below 50, always with the number), form and starter/bench/not-in-squad. Edits go through `useCareer().setLineup` / `setTactics` / `autoPickLineup`; a rejected lineup shows `squad-error` and changes nothing. A plan edit is not saved on its own; the next autosave (matchday, new season) carries it. `matchSetupFor` already plays the saved plan.
- The career lives in `useCareer` (`use-career.tsx`), an in-memory store. M4 plugs the `SaveStore` in there without changing screens. Without a career every route except `#/match` shows the new-career screen.
- `#/league` (`league-screen.tsx`) has a Table tab (`league-table.tsx`, built from `computeTable`) and a Fixtures tab (`fixtures-view.tsx`). `LeagueView` takes the career as a prop; `LeagueScreen` reads it from `useCareer`, so new results show without a reload.
- Season flow: the hub shows the next match with "Play match" (`#/match`, `MatchFlowScreen` feeding `MatchScreen` from `matchSetupFor`) and "Quick sim" (`simulateFixture`). Both record the result through `useCareer().completeMatch` (`completeMatchday`) and lead to `#/results`, which lists the round and the user's table position. After the last matchday `#/season-end` shows the `summariseSeason` summary and "Start next season". Guards: `#/match`, `#/results` and `#/season-end` redirect to the hub when there is nothing to show. Leaving a match mid-way records nothing and the next visit restarts from kickoff.
- `App` takes `saveStore`, `fileTransfer`, `now` (ISO clock) and optional `storageAvailable` next to `localeStore`. `main.tsx` passes the IndexedDB store, or the memory store with `storageAvailable={false}` (which shows `StorageWarning`). `CareerProvider` autosaves through the `SaveStore` and exposes `saveStatus`, `lastSavedAt`, `continueAvailable`, `continueInfo`, `loadAutosave()`, `loadError` and `dismissLoadError()`; the header shows `SaveStatus` and the new-career screen shows `ContinuePanel` (Continue button or load error).
- The saves screen (`saves-screen.tsx`, `save-slots.ts`) at `#/saves` lists the `autosave` slot and manual slots `slot-1` to `slot-3` and works without a career (only loading is enabled then). Rows are built with `readSlot` (`readEnvelope` + `parseCareer`); a damaged slot shows "Corrupt save" with only Delete and never breaks the screen. `useCareer` exposes `listSlots()`, `saveToSlot(id)`, `loadSlot(id)` and `deleteSlot(id)`, which return `{ ok } | { ok: false, error }` and never throw. Manual saves get a fresh envelope (`createdAt` and `savedAt` = time of the write); rows show `savedAt`; the autosave slot cannot be written manually. Overwriting a used slot and deleting ask for confirmation; loading replaces the running career without asking and leads to the hub.
- Export and import (`import-save.ts`, `import-controls.tsx`): `App` and `CareerProvider` take a `fileTransfer`; `main.tsx` passes `createBrowserFileTransfer()`. Filled slot rows have "Export" (the stored, migrated envelope via `serializeSave`, named by `saveFileName`) and the saves screen has "Export running career" while a career exists. "Import file" (saves screen and new-career screen) runs `pickFile`, `parseSaveFile` and `parseCareer`; a valid file becomes `importOffer` and the saves screen asks for a manual slot (`import-into-<id>`), confirming before overwriting a used slot, then stores the envelope with its original `createdAt` and highlights the slot (`data-highlighted`). It never replaces the running career. Failures set `importError` (`not-json`, `not-a-save`, `newer-version`, `file-too-large`, `corrupt-career`), shown as `import-error`; cancelling the picker is silent. On the new-career screen a valid pick navigates to `#/saves`.
- The composition root passes `initialSeed` to `App`, so the UI itself never draws randomness and tests stay deterministic.

## Game state (squad plan and condition)

- `Career.squadPlan` (`SquadPlan = Lineup & { tactics }`, `squad-plan.ts`) is the user's formation, starters, bench and tactics. `Career.condition` maps every league player id to `PlayerCondition` (fitness 0..100, form 1..10). Both are plain JSON. `createCareer` starts with `autoPickLineup` for 4-4-2, `NEUTRAL_TACTICS` and `initialConditions`.
- `matchInputFor` derives the user's sheet from the plan and `condition` (effective attributes), and the user's tactics from the plan. AI clubs always play `autoPickLineup` 4-4-2 from the current condition with neutral tactics.
- Edits are pure (`edit-squad-plan.ts`): `setLineup(career, lineup)` validates with `validateLineup` and returns `{ ok, career } | { ok: false, error }`, `setTactics(career, tactics)` and `autoPickUserLineup(career, formation)` return a new career.
- Condition per matchday (`update-condition.ts`): `completeMatchday(career, userResult, report?)` plays every fixture with the condition as it was before the round, then `updateConditionAfterMatchday` applies `applyMatchToCondition` and `recoverCondition` to every player. `MatchReport = { minutes: Record<playerId, number> }` gives the user's minutes (absent players played 0); without a report the user's starters count as 90 minutes, which is what the quick sim and `useCareer().completeMatch(result)` pass. AI clubs get 90 minutes for the eleven `autoPickLineup` picks (4-4-2, pre-round condition), 0 for the rest, so tired AI starters rotate out. `startNextSeason` resets every player to full fitness and form 5 and keeps `squadPlan`.
- Half-time (`plan-half-time.ts`): `planHalfTime(career, fixture, { substitutions, tactics? })` is pure and never changes the career. It validates at most `MAX_SUBSTITUTIONS` (5) substitutions in one window, each `{ off, on }` with `off` a starter, `on` a bench player of the same position and nobody used twice (errors `too-many-substitutions`, `duplicate-substitution`, `player-not-on-pitch`, `player-not-on-bench`, `position-mismatch`; checked in that order). It returns `{ ok: true, change, report, lineupAfter }`: `change` is the engine `ActionMatchChange` for the user's side (`lineup`: the `EnginePlayer`s of `lineupAfter` in slot order at the current condition, substitutes in the starters' slots, plus the new or unchanged tactics), `report` is the `MatchReport` (starters who stay 90, substituted off 45, came on 45, unused bench 0) and `lineupAfter` has the substitutes in the starters' places and the substituted-off players on the bench slots they left (same formation, valid bench). The UI calls `match.applyChange(change)` at half-time, then `match.resume()`, and passes `report` to `completeMatchday` when the match ends. The same seed, plan and moment give the same match.
- `parseCareer` rejects a bad plan (`invalid-squad-plan`: formation shape, bench size, duplicate, unknown or foreign ids, unknown tactics values) and a bad condition (`invalid-condition`: out-of-range values, a missing or an unknown player).

## Commentary

- Templates live per locale (`en`, `sv`) in `src/commentary/templates` with several variants per key (a test enforces both locales have the same keys and the same placeholders). Grammar helpers such as the Swedish genitive are in `grammar.ts`.
- Commentary is pure and uses its own RNG stream (`createRng(seed).fork("commentary")`), so it never changes the simulation.
- `generateActionCommentary(events, context, seed)` turns the action log into feed lines. `ActionCommentaryContext` has `locale`, `names` (teams) and `players` (id to display name). Templates live in `templates/action-en.ts` and `action-sv.ts` (same keys, a test lists the placeholders each key may use). It names players for goals (scorer and key passer), penalties, big chances and saves (shooter and keeper), key passes, through balls, tackles and interceptions that stop a dangerous attack, fouls (offender), corners, free kicks and, only occasionally, throw-ins and goal kicks, plus kickoff, half-time, full time and 15-minute possession summaries from `computeActionStats`. Which actions get a line is documented and tuned in `action-selection.ts` (always: goals, penalties, corners, big chances; sampled by xG, distance to goal and outcome: the rest) and keeps the feed at about 60 to 100 lines per match. A line depends only on the events up to its own, so regenerating from a growing log keeps earlier lines unchanged.

## Persistence

- `SaveStore` interface: `list()`, `load(id)`, `save(id, data)`, `delete(id)`.
- `createIndexedDbSaveStore(factory?, dbName?)` (`src/platform/save/indexeddb-save-store.ts`) is the browser implementation: database `touchline` version 1 with one object store `saves` keyed by save id. Every call opens, uses and closes its own connection; open, read and write failures (including blocked opens and aborted transactions) reject with a clear `Error`. `isIndexedDbAvailable()` tells the app when to fall back to the in-memory store. The `indexedDB` global is read only inside these functions, never at import time. It runs the shared `runSaveStoreContract` suite against `fake-indexeddb` (dev dependency).
- Engine version (schemas v4 and v5): `Career.engineVersion` (the engine for new matches, always 2) and `Result.engineVersion` (the engine a match was played on; results from the zone engine stay 1, a label only). The v3 to v4 migration (`addEngineVersion` in `src/game`) set both to 1; the v4 to v5 migration (`useActionEngine`) sets the career to 2 and leaves every result as it is. `parseCareer` rejects a career that is not on engine 2 (`invalid-engine-version`) and a result with an unknown value (`invalid-season`). `matchInputFor(career, fixture)` builds the `MatchInput` (`TeamSheet`s from `toEnginePlayers`/`toEngineBench`, `formationShape`; effective attributes are clamped to the engine's 1 to 20; goalkeepers keep the generator's weak passing and ball control, which only matters for distribution). `simulateFixture` plays matches with `createActionMatch(..., { detail: "fast" })` and stamps the version, and `completeMatchday` rejects a user result from another engine (`wrong-engine-version`). The new-career screen has no engine choice. Old results are never replayed, so removing the zone engine only means the number 1 stays a label.
- Save format: `{ schemaVersion, createdAt, savedAt, game }` (`createdAt` is when the career was first saved and survives re-saves; `savedAt` is the time of the last write), with a migration per version bump.
- Codec (`src/platform/save`): `createEnvelope(game, now)` and `updateEnvelope(previous, game, now)` build envelopes (the clock is injected; re-saving keeps `createdAt` and sets a new `savedAt`), `readEnvelope(raw)` migrates an untrusted blob to `CURRENT_SCHEMA_VERSION`, rejects one without a valid `savedAt` (`invalid-envelope`) and returns `{ ok, save } | { ok: false, error }`. The codec is game-agnostic (`game: unknown`); the caller runs `parseCareer` afterwards.
- Versioning rule: `schemaVersion` 1 is the M3 `Career` shape; version 2 adds `savedAt` to the envelope (migration: `savedAt = createdAt`); version 3 adds `Career.squadPlan` and `Career.condition` (migration: `addSquadPlanAndCondition` from `src/game` gives the 4-4-2 best eleven, neutral tactics and full condition, so a migrated career plays like before; data it cannot read is left for `parseCareer` to reject); version 4 adds `Career.engineVersion` and `Result.engineVersion` (migration: `addEngineVersion`, both 1); version 5 moves every career to the action engine (migration: `useActionEngine`, `Career.engineVersion` 2, results untouched); version 6 adds the optional `Result.scorers` (migration only bumps the version; `parseCareer` checks that scorers add up to each club's goals and belong to the scoring club). Every change to `Career` or the envelope bumps `CURRENT_SCHEMA_VERSION` in `schema.ts` and adds a `Migration` to `MIGRATIONS`; a test fails if the list is not a gapless chain from 1.
- Fixture policy: `fixtures/career-v1.json` to `career-v6.json` are real saves, frozen and never regenerated (`career-v4.json` is an engine 2 career after two matchdays; `career-v5.json` is a schema v5 career after two matchdays; `career-v6.json` is a schema v6 career with recorded scorers after two matchdays). A bump adds the next fixture and keeps the older ones, so old saves keep loading.
- Saved and imported data is untrusted: `parseCareer(raw)` in `src/game` rebuilds a `Career` field by field and returns `{ ok, career } | { ok: false, error }` (never throws, never returns the input). Every stored `game` payload goes through it before the UI uses it.
- Save files (`src/platform/save/save-file.ts`): `serializeSave(envelope)` writes pretty-printed JSON; `parseSaveFile(text)` rejects files above 10 MB (`file-too-large`), non-JSON (`not-json`) and otherwise delegates to `readEnvelope`, so it adds no version logic of its own (`invalid-envelope`, `newer-version`, `missing-migration`). `saveFileName({ clubName, season, matchday })` gives `touchline-<club-slug>-s<season>-md<matchday>.json` with Swedish letters folded to ASCII and a safe fallback slug.
- `FileTransfer` (`src/shared`): `download(name, text)` and `pickFile()`. `createBrowserFileTransfer()` uses Blob + object URL (revoked after the click) and a hidden file input; `createMemoryFileTransfer()` records downloads and returns queued files for tests. A Tauri adapter can replace the browser one.
- Autosave (`src/ui/autosave-queue.ts`): slot `autosave`, written after the career is created, after every completed matchday and after starting the next season, never mid-match. `createAutosaveQueue(store, now)` runs writes strictly one after another so the last state wins; `save(game, "new" | "continue")` starts a new `createdAt` or keeps the current one (`adopt` marks a loaded envelope as the one to continue). A failed write rejects only its own promise and never blocks play.
- Startup (`src/ui/find-continue-candidate.ts`): `findContinueCandidate(store)` reads the autosave (or the newest valid save by `savedAt` when there is none) through `readEnvelope` and `parseCareer`. A damaged or newer-version autosave is returned as an error and never falls back to another slot. Nothing is loaded until the user presses Continue.
- E2E (`e2e/persistence.spec.ts`): reload and continue (tagged `@smoke`), manual slot save and load, export a slot and import the downloaded file into another slot, and rejecting a garbage file. Each test runs in a fresh browser context, so IndexedDB starts empty.
- E2E (`e2e/squad-and-tactics.spec.ts`): the M5 flow. Set formation, pressing, tempo and a bench swap on the squad screen; play a match with a half-time substitution and a mentality change; check fitness and form on the squad screen; reload, press Continue and see the plan kept. The derived ratings change with formation and lineup only, not with tactics. A `@smoke` variant changes one tactic, plays a quick-sim matchday (a plan edit is only saved by the next autosave), reloads and checks it is kept.
- E2E (`e2e/match-engine.spec.ts`): the match flow. A `@smoke` test quick-sims a matchday and checks the table. The full test plays a match at speed 4 with the momentum and pitch views, the passing-chain toggle (on by default), a half-time substitution and a mentality change, checks the ratings table and player of the match, continues to the results, reloads and presses Continue, then exports a slot (`engineVersion` 2) and imports it into another slot.
