# Vision

## Concept

A football management game inspired by Football Manager, but smaller: fewer screens and attributes, faster seasons, still real depth in tactics, squad building and player development. Played mainly on desktop, in the browser.

## Core loop

1. Pick a fictional club in a generated league.
2. Set lineup, formation and tactics.
3. Play matches in the momentum match view, react at half-time (substitutions, tactics).
4. Manage the squad between matches: training focus, transfers, contracts, youth.
5. Finish the season, get promoted or relegated, continue the next season.

## Decisions

| Topic | Decision |
|---|---|
| Platform | Desktop browser first (1280 px and wider), but every screen is also designed for tablet and phone widths in M5c (see "UI overhaul (M5c)"). |
| Stack | TypeScript, Vite, React for screens, three.js for the match view. Chosen because coding agents work well with it. |
| Hosting | GitHub Pages (free). Later packaged as a desktop app with Tauri. |
| Backend | None. Single player, all logic runs in the client. |
| Saving | IndexedDB behind a `SaveStore` interface, autosave, export/import as JSON. Tauri file storage later. |
| Data | Fully fictional clubs, players and leagues. No licensing issues. |
| Language | Repo in English. Game in English and Swedish. |
| Match engine | Deterministic, seeded, **action-level** engine (`src/engine/action`): players, not team ratings, drive the simulation. One action (pass, carry, shot, tackle, interception, clearance, foul, set piece) every 2 to 4 match seconds, each with an actor, an optional target, from/to positions in metres, an outcome, pressure and, for shots, xG. The event log drives the match view, commentary, stats and ratings. History: the first engine (v1) was a zone-based state machine over seven team phase ratings; it was replaced in M5b and deleted in #167. |
| Match view | Animated 3D height map of the pitch: height shows pressure, colour shows which team dominates, the front between colours moves with territory. Big spike and shockwave on goals. No players or ball drawn. |
| Quality | TDD, high coverage, balance tests on the engine, nightly mutation testing. |
| Cost | Everything free: tooling, hosting, CI. |
| League size (M3) | One league with **14 clubs**, double round-robin (each pair meets home and away), 26 matchdays. The size is a parameter (even number, 12 to 16) so it can change without rewrites. |
| Player attributes (M3) | **12 attributes**, integers 1 to 20: passing, ball control, dribbling, pace, vision, finishing, work rate, tackling, positioning, strength (outfield) and handling, reflexes (goalkeeper). Fitness and form turn them into effective attributes, which are what the engine plays with. The screens show line ratings (goalkeeping, defence, midfield, attack and overall, 0 to 100) from the mean of each position's key attributes, see `docs/architecture.md`. |
| Season format (M3) | Single league, no promotion or relegation yet. At season end the champion and final table are shown and the user can start the next season with the same clubs (new fixtures, same ratings until player development arrives in M6). Promotion and relegation need several divisions and are a later milestone. |
| Table tie-breakers (M3) | Points, then goal difference, then goals scored, then head-to-head points, then club name (alphabetical) as a final deterministic fallback. |
| Matchday flow (M3) | The user's match is played in the match view or skipped with a quick sim (same engine and seed, no animation). All other matches of the round are simulated instantly with the same engine when the matchday is completed. Matchdays are played in order; the user cannot skip a matchday. |
| AI lineups (M3) | Until the squad and tactics milestone (M5), every club (including the user's) plays its best eleven in a fixed 4-4-2 picked automatically from the squad. Replaced by the M5 rows below. |
| Home advantage | A small, named and tunable `HOME_ADVANTAGE` in the engine (target home win rate of 42% to 48% between equal teams). |
| Game state shape | All career and season state is plain JSON-serialisable data (no `Map`, `Set`, `Date`, classes or functions) so M4 can save it unchanged. Entities reference each other by string id. All randomness derives from the career seed through `createRng(...).fork(name)`. |
| Save slots (M4) | One **autosave** slot (`autosave`) plus **3 manual slots** (`slot-1` to `slot-3`). One running career at a time. |
| Autosave (M4) | The career is autosaved after it is created, after every completed matchday and after starting the next season, never mid-match (leaving a match restarts it from kickoff, as in M3). On startup the app offers "Continue" from the autosave (or the newest save when the autosave is missing). Autosave failures are shown but never block play. |
| Save content (M4) | A save stores the `Career` (plain JSON, see "Game state shape") inside the `SaveEnvelope`. `schemaVersion` **1** is the M3 `Career` shape and **2** adds `savedAt` (time of the last write; v1 saves get `savedAt = createdAt`); `createdAt` stays the time of the first save. Every later change of that shape bumps the version and ships a migration with a test and a frozen fixture. The locale preference is not part of a save (it stays in `localStorage`). `createdAt` comes from a clock injected at the composition root, because `game` must not read the time. |
| Export and import (M4) | Export writes the envelope as pretty-printed JSON, file name `touchline-<club-slug>-s<season>-md<matchday>.json`. Import validates and migrates the file and stores it in a manual slot the user picks (confirming before overwriting a used slot); it never replaces the running career directly. Invalid or newer-version files are rejected with a message. |
| Storage fallback (M4) | If IndexedDB is unavailable (private mode, blocked storage) the app falls back to the in-memory store, shows a persistent warning that progress will be lost on reload, and export still works. |
| Test dependency (M4) | `fake-indexeddb` (MIT, dev dependency only) lets the IndexedDB adapter run the `SaveStore` contract suite in Vitest. No new runtime dependency. |
| Formations (M5) | Six formations written as DEF-MID-FWD: **4-4-2, 4-3-3, 4-5-1, 3-5-2, 5-3-2, 3-4-3**, always with 1 GK. Positions stay four lines (GK, DEF, MID, FWD) and a player only plays in their own line (no out-of-position penalty model yet). The generated squads (3 GK, 7 DEF, 7 MID, 5 FWD) can fill every formation. A formation is a real shape in the engine (anchor positions per slot), and no formation may dominate: none wins or loses more than 55% of its matches against an equal-strength 4-4-2 (`formation.balance.test.ts`). The formation is fixed for a whole match: it cannot change at half-time. |
| Matchday squad (M5) | 11 starters plus **7 substitutes** (at least one GK); the other four squad players are not in the matchday squad. The user picks lineup and bench in the squad screen; "Auto-pick" fills both. Players not in the starting eleven earn no minutes. |
| Tactics (M5) | Four settings with three levels each: **mentality** (defensive, balanced, attacking), **pressing** (low, medium, high), **width** (narrow, normal, wide), **tempo** (slow, normal, fast). The neutral setting (balanced, medium, normal, normal) is the baseline. The engine turns the settings into team-shape and decision parameters: pressing sets line height and press trigger, width sets width, mentality and pressing together set compactness, tempo and mentality set directness and risk. Each setting has a bounded effect with a risk side (for example high pressing gives more turnovers high up but exposes the team to chances), and no combination of the 81 may dominate. |
| Out-of-position play (#281) | A player is rated at the position he or she plays (`positionRating` in `src/game`). Playing outside the own position scales every attribute by `1 - penalty` (never below 1); the penalty depends on the distance between the four lines and is symmetric: **0** at the own position, **0.10** one line away (DEF/MID, MID/FWD), **0.20** two lines away (DEF/FWD), **0.50** between goalkeeper and any outfield position, in both directions. Further away is never better. The constants are named (`OUTFIELD_ONE_LINE_PENALTY`, `OUTFIELD_TWO_LINES_PENALTY`, `GOALKEEPER_SWAP_PENALTY`). `toEnginePlayers` takes an optional map of played positions (default: own position), so the lineup and changes (#266) can put anyone anywhere; nothing is locked out. |
| Changes during a match (M5) | Decided in #266. **Substitutions:** up to **5 per match** over **3 windows plus half-time**; any player may replace any other, whatever the position (nothing is locked out). A player substituted off cannot return; a substitute who came on may later be substituted off (uses another of the five). **Position rating:** a player is rated at the position they actually play, so a striker at right back or an outfielder in goal gets a lower rating there; the UI shows this rating when picking a change. **Minutes** are the real time on the pitch, derived from the engine's `ActionMatch.changes`. **Shouts:** temporary, bounded tactics modifiers (for example "Push up", "Calm it down") for N minutes with a cooldown, applied through `applyChange`; pressing and a higher mentality drain stamina more, so shouts have a cost and must not make a tactic dominant. **Shouts as built (#266):** Push up (mentality up), Calm it down (mentality down), Press the ball (pressing and tempo up) and Hold shape (pressing and tempo down); each lasts 10 minutes, then 10 minutes of cooldown for any shout; raising mentality or pressing costs 0.05 extra fitness per level and minute. **AI (#291):** at half-time and minutes 60, 70 and 80 an AI club replaces up to two of its most tired outfield starters (fitness 65 or lower at that minute) by the strongest same-position bench player who is at least 10 fitness points fitter (five in all), and from minute 60 shouts Push up when behind and Calm it down when ahead, within the shout duration, cooldown and fatigue cost. **Timing:** changes only while paused; "Make changes" pauses automatically. Injuries do not exist, so there are no forced substitutions. |
| Fitness and form (M5) | Per player, stored in `Career.condition`, not on `Player` (attributes stay fixed until M6). **Fitness** 0 to 100, starts at 100: playing 90 minutes costs 10 (proportional to minutes), and after every matchday every player recovers 25% of the missing fitness. **Form** 1 to 10, starts at 5: after a match a player who played at least 45 minutes gains 1 for a win, loses 1 for a defeat, a draw changes nothing. Effective attributes are the stored attributes times `0.85 + 0.15 * fitness / 100` times `1 + 0.01 * (form - 5)` (clamped to 1 to 20 for the engine). A new season resets fitness to 100 and form to 5. The constants are named and tunable. |
| AI clubs (M5) | AI clubs always use 4-4-2 and neutral tactics, pick their eleven and bench automatically by effective strength (so tired starters get rotated out) and, since #291, substitute and shout during a match (see "Changes during a match"); they never use the user's changes or knowledge, only the match situation. Varied AI styles come with the AI work in M6. |
| Squad plan and save version (M5) | The user's choices live in `Career.squadPlan` (formation, starters, bench, tactics) and fitness and form in `Career.condition`. This is `schemaVersion` **3**; the migration gives old saves the 4-4-2 best eleven, neutral tactics and full fitness. |
| Engine-owned team shape | The engine, not the view, decides where all 22 players stand at every action: from formation, tactics (line height, width, compactness), phase of play and ball position. Positions are part of the event (a snapshot) and views only interpolate between snapshots. There is no per-tick physics. |
| Match clock | The clock runs continuously and dead time is compressed: restarts (throw-in, goal kick, corner, free kick, kickoff) are actions of 2 to 4 seconds like any other. Ball-in-play time is not modelled. A match has about 1,800 to 2,000 actions. |
| Player stats and ratings | Stats gain pass completion, key passes, per-player shots and xG, and a 1 to 10 player rating computed from events. Ratings are derived data, never stored in saves. |
| Engine version field | `MatchInput.engineVersion` (2) is kept for a future engine and every recorded result stores the version it was played with; results from the zone engine keep the label 1 and are never replayed. |
| Save versioning for the engine | `schemaVersion` **4** added `Result.engineVersion` and `Career.engineVersion`; **5** (#167) moves every career to the action engine (`Career.engineVersion` 2) and leaves recorded results as they are. |
| Recorded scorers (#216) | `Result.scorers` lists the player id of every goal in the order the goals were scored (both sides mixed), taken from the action log by `simulateFixture` and from the match screen for the user's match. This is `schemaVersion` **6**; the migration changes nothing (the field is optional), so results from older saves have no scorers and the season summary still draws their scorers with `pickGoalScorers`. `parseCareer` rejects scorers that do not add up to each club's goals or belong to another club. |
| Scope of M6 | **Deliberately simple.** The M6 rules are pragmatic defaults, not final design: the economy, transfer rules, AI behaviour and contracts are expected to change once the core epics are done and the game can be judged as a whole, so implement them plainly and do not add depth or flexibility beyond the issue. Growth and decline, contracts and wages, a simple club economy, a transfer market, youth intake and retirement. **Not in M6:** training focus (growth depends on age, potential and minutes only, so the core loop's "training focus" waits for M8 or later), varied AI styles (AI clubs stay 4-4-2 with neutral tactics), injuries and suspensions, promotion and relegation, scouting, loans, agents, clauses. |
| Potential (M6) | `Player.potential`, integer 1 to 20: the highest `playerOverall` the player can reach. Never below the current overall. Generated at career creation: age 16 to 20 gets overall + 3 to 7, 21 to 24 gets + 1 to 4, 25 and older gets + 0 to 1 (clamped to 20). The user sees it as 1 to 5 stars (no scouting model: potential is visible for every player). |
| Ageing and growth (M6) | Everything changes once a year, at the season rollover (`finishSeason`): age + 1, then development. Until 24 a player closes a share of the gap to potential (peak at 18 to 21) and may still lose nothing; 25 to 29 is a plateau (changes of -1 to +1); from 30 attributes decline, physical ones first (pace, strength, work rate), technical ones later, faster each year. Playing time scales growth only: a factor from 0.5 (under 450 minutes in the season) to 1.25 (1,800 minutes or more). An attribute changes by at most 3 per season, stays an integer in 1 to 20, and the position's overall never exceeds `potential`. All constants are named and tunable; randomness comes from `createRng(seed).fork("development-<season>")`. |
| Playing time (M6) | `Career.minutes` (season minutes per player id, whole league) accumulates in `completeMatchday` from the real minutes of the user's match (incl. half-time substitutions) and the real minutes of AI clubs (their substitutions included). It resets at the rollover. |
| Retirement (M6) | From age 34 a player retires at the rollover with probability 15% at 34, rising by 15 points a year, certain at 38. Retired players are removed from the league data (their old results stay valid because results only store ids and goals; scorer names in summaries are resolved at summary time). |
| Money (M6) | Amounts are integers in thousands of a fictional euro, shown as e.g. "€1.2M" in both locales. A `ClubFinance` per club: `{ balance, baseIncome }` in `Career.finances`. Wages are paid per season, deducted at the rollover together with income: `baseIncome` (set at career creation in proportion to the club's initial squad value, so strong clubs are richer) plus a prize that falls linearly from 1st to last place. Balances may go negative: there is no bankruptcy, no sacking and no board. A club may not spend more than its balance on fees, and its wage bill may not exceed 75% of `baseIncome` (the wage budget). The same rules bind AI clubs. |
| Player value and wage (M6) | One named formula gives a player's `value` from overall, age, potential and remaining contract (young high-potential players are worth more, value falls to near zero at 35). The wage a player asks is a fixed share of value per season, so wage and value stay consistent. Asking price of a transfer = value. |
| Contracts (M6) | `Career.contracts[playerId] = { wage, expiresSeason }`. New players (generated at career creation, youth, signings) get 1 to 5 seasons, youth 3. A contract ends after the final match of `expiresSeason`. The user can renew in the off-season window (the player accepts any wage at or above his ask; a new length of 1 to 5 seasons is chosen). Unrenewed players join the free-agent pool (`Career.freeAgentIds`; they keep their `Player` record in `league.players`). AI clubs renew every expiring player who is in their best 18 or aged 23 or under, and let the rest go. |
| Transfer rules (M6) | Transfers between clubs only happen in the **off-season window**: after the season summary, before the user starts the next season. Free agents can be signed at any time. The user can buy any player of an AI club at a fee of at least his value (1.3 times the value if he is in that club's best eleven); the AI accepts at once (deterministic, no negotiation rounds) unless the sale would drop the club below the squad minimum. AI clubs never trade with each other; they only sign free agents and youth and release players. The user sells by accepting **offers**: when the window opens each AI club with a need can make an offer (0.8 to 1.2 times value, at most 5 offers in total, drawn from the seeded rng) and the user can accept or ignore them, or release a player (no fee, no further wages). Signing a player pays the fee at once and starts his wage at the next rollover. |
| Squad size (M6) | Between 18 and 30 players per club, with at least 2 GK, 5 DEF, 5 MID and 3 FWD (the generated squads of 22 satisfy this). Buying or signing is refused above 30, selling or releasing below the minimums. If a player in the user's `squadPlan` leaves, the plan is repaired with `autoPickLineup` (same formation and tactics). If the user's squad is over 30 after youth intake, starting the next season is blocked until they release enough players. AI clubs release their lowest-value surplus players automatically. |
| Free-agent pool (M6) | The pool is capped at `FREE_AGENT_POOL_CAP` (**40**) players. At the end of `startNextSeason`, after the AI clubs filled their holes, the least wanted free agents are removed until the pool fits: lowest `value` first, ties by id (lower id first). Removed players disappear from the league like retirees (`league.players`, contracts, condition, minutes). The rule is deterministic, needs no randomness and does not depend on the order of clubs. |
| Youth intake (M6) | At the rollover every club gets 3 youth players, age 16 to 18, positions chosen to fill the club's thinnest lines, quality drawn from a per-club `youthQuality` (a fixed function of the club's initial strength plus seeded noise, so strong clubs tend to get better youth), potential per the rule above. They join the squad directly on a 3-season contract (no separate academy squad). |
| Off-season order (M6) | At the rollover (`finishSeason`): summary of the finished season, finances (the wages of the season just played, so before contracts end), age + 1, development, retirement, AI contract renewals and releases, youth intake. Then the window opens: the user's renewals, free agents, offers, market. The user's unrenewed players leave when he starts the next season (`startNextSeason`), which needs a legal squad of 18 to 30 players; AI clubs then fill their holes from the free-agent pool. Everything draws from `createRng(seed).fork("offseason-<season>")` streams so results do not depend on the order of clubs. |
| Save version for M6 | `schemaVersion` **7** adds `Player.potential`, `Career.contracts`, `Career.finances`, `Career.freeAgentIds` and `Career.minutes`; the migration derives all of them deterministically from the career seed and the stored players (potential from age and overall, contract lengths spread over 1 to 5 seasons, base income from squad value). Every later M6 change to the stored shape stays inside these fields, plus two optional fields that are not in the migration (an old save simply has none): `Career.lastDevelopment` (the change list of the last yearly development, for players still in the league) and `Career.lastRollover` (the user's retired players with their age and position, and the income and wages of the season just played). Both are replaced at every rollover and feed the off-season review. |
| Long-run balance (M6) | Over 10 simulated seasons the league must not drift: the mean best-eleven overall of all clubs stays within 0.75 attribute points of the starting value, the gap between the strongest and weakest club stays between 50% and 200% of the starting gap, and no club's squad falls below the minimums. A multi-season balance test (`development.balance.test.ts`) enforces this. Engine balance tests are unaffected, because the engine only sees attributes. |
| Names | Club, player and league names are generated data (proper nouns), not UI strings, so they are not translated. Pools are Swedish-flavoured fictional names. |
| UI overhaul (M5c) | A full UI overhaul, direction **"Floodlight"**: dark-first, calm, rounded, Barlow Condensed and Barlow with tabular numbers. Three themes (Midnight default, Graphite, Light), selectable in settings and remembered; amber `#FFB547` is the app accent (primary actions, focus, highlights), club colours are identity only (crest, scoreboard, the user's table row, match visuals, never buttons); pitch and match visuals sit on a dark stage in every theme. Sidebar, icon rail and bottom tab bar by width, command palette on Ctrl/Cmd+K, a start flow (continue, load, league, club), compact tables that become cards on phones, and a match screen with a side panel that becomes tabs. WCAG 2.2 AA, 44 px touch targets, reduced motion, English and Swedish. Stack: React, Tailwind CSS v4 on CSS custom property tokens, Radix UI primitives in shadcn/ui-style owned components, lucide icons, Motion, Storybook, all free. Details, tokens, boards (`reference/ui/`) and the issue plan: `docs/design.md`, epic #246. Mobile and polish scope moved here from M8. |
| Kits (M5c) | Every club has a home kit (primary body, secondary trim) and an away kit (secondary body, primary trim), derived from the club colours (no save change). If the two home kit body colours are closer than a tested threshold the away team wears its away kit; the match view, scoreboard and stats use the colours worn. |
| In-match energy (#385) | Players tire during a match. Energy (0 to 100) drains per minute with work rate, pressing, tempo and role and lowers every attribute by up to 30% (about 7% for a neutral starter over 90 minutes). Rules and constants: `docs/architecture.md`, "In-match energy". Substitutes start fresh, so rotating tired players matters. The post-match fitness drain follows the energy a player spent (#413), see `docs/architecture.md`. |

## Out of scope (for now)

Multiplayer, real teams or players, rendering of players or ball, online accounts, monetisation.

## Open questions

All open questions, and the M6 defaults above, are to be revisited together after the core epics are done (candidates: AI-to-AI transfers, a deeper economy, in-game substitutions beyond half-time, more leagues and cups). Do not try to settle them earlier.

- ~~How many leagues and divisions in the first playable version?~~ Decided for M3: one league, 14 clubs (see Decisions). Several divisions with promotion and relegation: when?
- ~~How detailed should player attributes be?~~ Decided for M3: 12 attributes (see Decisions). Player development in M6 uses the same 12 attributes (see Decisions).
- ~~How are saves organised?~~ Decided for M4: autosave plus 3 manual slots, JSON export/import (see Decisions). Cloud sync stays out of scope.
- In-match tactical changes beyond half-time: decided for M5 that only half-time changes exist (see Decisions). Changes at any moment of the match: when in the roadmap?
- Out-of-position play, injuries and suspensions: when? None exist in M5.
- Mid-match saves (resume exactly where a match stopped) do not exist; with v2 the match input would have to be stored together with `engineVersion`. When?
- Training focus (listed in the core loop) is not part of M6: which milestone? Varied AI styles and AI-to-AI transfers are also deferred.
- Promotion and relegation (several divisions): when? The M6 economy has no consequence for relegation.
- Final name of the game.
